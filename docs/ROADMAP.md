## 개요

How's your Christmas는 **일본 10~20대 여성과 그 친구들(한국 출시도 예정)**을 위한 **"편지를 주고받을수록 함께 꾸며지는 크리스마스 마을"**로, 다음 기능을 제공합니다:

- **3D 마을 걷기 (F001)**: 광장·대왕 트리·주민 집·우체통이 있는 미니어처 3D 마을을 휴대폰 브라우저에서 걸어 다닙니다.
- **편지 보내기·확인하기 (F004~F006)**: 친구 집 우체통에 이름을 쓴 편지를 넣고, 12.25에 잠금이 풀리면 개봉 연출과 함께 읽습니다. 12.25 전까지는 수정·삭제할 수 있습니다.
- **크리스마스 장식하기 (F003, F008)**: 마을 전체의 "보낸 편지 / 써야 할 편지(n(n-1)통)" 비율이 10% 오를 때마다 장식표의 다음 단계 장식이 추가되고, 100%에 대왕별과 폭죽이 나옵니다.
- **낮/밤 배경 (F002)**: 사용자가 낮/밤을 직접 고르고, 밤에는 가로등이 켜집니다.
- **LINE·카카오 로그인과 초대 링크 (F010~F013)**: 링크로 들어와 로그인하면 바로 주민이 되고 집이 자동으로 생깁니다.
- **크리스마스 당일 연출·인증샷·알림 (F007, F014, F018)**: 12.25~12.26 특별 연출, 모두 모여 찍는 인증샷, LINE·카카오톡 알림.

## 개발 워크플로우

1. **작업 계획**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- 새로운 작업을 포함하도록 `ROADMAP.md` 업데이트
- 우선순위 작업은 마지막 완료된 작업 다음에 삽입

2. **작업 생성**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- `/tasks` 디렉토리에 새 작업 파일 생성
- 명명 형식: `XXX-description.md` (예: `001-setup.md`)
- 고수준 명세서, 관련 파일, 수락 기준, 구현 단계 포함
- **API/비즈니스 로직 작업 시 "## 테스트 체크리스트" 섹션 필수 포함 (Playwright MCP 테스트 시나리오 작성)**
- 예시를 위해 `/tasks` 디렉토리의 마지막 완료된 작업 참조. 예를 들어, 현재 작업이 `012`라면 `011`과 `010`을 예시로 참조.
- 이러한 예시들은 완료된 작업이므로 내용이 완료된 작업의 최종 상태를 반영함 (체크된 박스와 변경 사항 요약). 새 작업의 경우, 문서에는 빈 박스와 변경 사항 요약이 없어야 함. 초기 상태의 샘플로 `000-sample.md` 참조.
- 참고: 아직 `/tasks` 디렉토리와 `000-sample.md`가 없습니다. Task 001을 시작할 때 함께 만듭니다.

3. **작업 구현**

- 작업 파일의 명세서를 따름
- 기능과 기능성 구현
- **API 연동 및 비즈니스 로직 구현 시 Playwright MCP로 테스트 수행 필수**
- 각 단계 후 작업 파일 내 단계 진행 상황 업데이트
- 구현 완료 후 Playwright MCP를 사용한 E2E 테스트 실행
- 테스트 통과 확인 후 다음 단계로 진행
- 각 단계 완료 후 중단하고 추가 지시를 기다림

4. **로드맵 업데이트**

- 로드맵에서 완료된 작업을 ✅로 표시

> **3D 화면 테스트 요령**: Playwright는 3D 그림(캔버스) 안의 물체를 직접 "읽지" 못합니다. 그래서 개발 환경에서만 보이는 **테스트용 표시**(예: 현재 장식 단계 숫자, 캐릭터 위치)를 화면에 두고, 스크린샷 비교와 함께 확인합니다. 12.25 잠금처럼 날짜에 따라 달라지는 기능은 **개발용 날짜 바꾸기 기능**(PRD 가정 23)으로 시험합니다.

## 개발 단계

> **구조 우선 접근법을 이 프로젝트에 맞춘 방식**: 원칙은 "골격 → 화면(더미 데이터) → 진짜 데이터 연결" 순서입니다. 다만 12.3까지 시간이 매우 짧아서, **Phase 2의 더미 화면은 12.3 범위 화면만** 만듭니다. 12.3 이후 기능(Phase 4)은 Task 하나 안에서 "화면(더미) → 데이터 연결 → 테스트" 순서를 지킵니다. 화면은 처음부터 **데이터를 가져오는 함수 한 곳**을 통해서만 데이터를 받게 만들어서, 나중에 더미를 진짜로 바꿀 때 그 함수만 고치면 되게 합니다(중복 작업 방지).
>
> **PRD 일정표와 순서가 다른 점**: PRD 표는 11.23~11.29에 로그인·편지 등 데이터 쪽을, 11.30~12.02에 3D 마을을 두었습니다. 이 로드맵은 **12.3 전/후 범위는 PRD와 같게** 두되, 순서는 구조 우선 원칙에 따라 화면을 먼저 만듭니다. 대신 로그인은 외부 심사·설정 문제가 생기기 쉬우므로 **신청은 Task 001에서 오늘 바로** 합니다.

- **Task 025: 함께 걷기 — 동시에 접속한 주민이 서로 걸어 다니는 모습 보이기** [여유 있으면] (약 7.5h, 11.27 사용자 요청으로 계획만 세움·아직 시작 전)
  - 지금은 내 화면에 내 캐릭터만 보임. 같은 마을에 동시에 접속한 주민의 캐릭터가 서로의 화면에서 걸어 다니고, 들어오면 나타나고 나가면 사라지게 함 (머리 위에 닉네임)
  - **방식**: Supabase 실시간 기능(Realtime)으로 마을마다 채널 1개. "지금 위치"를 계속 보내지 않고 **"걸어갈 목표"만** 보내고, 받는 쪽이 같은 길 찾기로 자기 화면에서 걷게 함. 이유: 무료 요금제 한도가 프로젝트 전체 초당 100 메시지·월 200만 메시지인데, 위치를 초당 10번 보내면 4명만 모여도 초당 160으로 한도를 넘음 (방송 1건 = 보낸 1 + 받는 사람 수로 집계)
  - **단계** (세부 내용은 작업 관리 도구 shrimp의 025-1 ~ 025-7에 있음. 앞 단계를 통과해야 다음 단계 시작):
    1. `025-1` 사전 점검과 기준선 측정 (약 0.5h): 요금제·실시간 설정·보안 상태 확인, 지금(0명) 그리기 시간 재기
    2. `025-2` 다른 주민 캐릭터 그리기 (약 2h): 네트워크 없이 가짜 주민으로 구동. 걷기 계산을 내 캐릭터와 같은 코드로 공유
    3. `025-3` **성능 시험: 얼마나 느려지는지** (약 1h): 0·1·3·5·10·19명 × 서 있음/걷기 × 낮/밤 × 휴대폰 흉내(CPU 4배 감속). 한 화면에 보여 줄 인원 상한을 정하고, **상한이 3명 미만이면 여기서 중단하고 보고**. 사용자의 실제 휴대폰 확인 포함
    4. `025-4` 실시간 채널 권한 규칙 (약 0.5h): 그 마을 주민만 듣고 보낼 수 있게, 비주민·비로그인 거부 확인
    5. `025-5` 위치 주고받기 (약 1.5h): 접속 상태 + 걸어갈 목표 방송. 환경 변수 `LIVE_WALK=1`일 때만 켜짐(기본 꺼짐)
    6. `025-6` 접속·퇴장과 예외 처리 (약 1h): 탭 숨김·끊김·로그인 갱신·새 주민 입주·같은 계정 두 탭
    7. `025-7` 통합 시험과 문서 (약 1h): 5명이 함께 있을 때의 메시지 수·지연·그리기 시간 측정, 기존 기능 회귀 확인
  - **지켜야 할 것**: 화질을 낮추는 방법 금지(해상도 낮추기 금지), 진짜 조명 추가 금지(발밑 둥근 가짜 그림자), 실시간 연결이 실패해도 걷기·편지는 그대로 동작, 위치가 와도 마을 화면 전체를 다시 그리지 않기
  - **점검에서 미리 확인한 사실 (11.27)**: 캐릭터 모델은 삼각형 6,377개·보이는 그리기 묶음 7개·뼈 41개 → 19명이면 그리기 호출이 약 133번 늘어남(밤에는 화면 효과 때문에 그 이상). 실시간 권한 표(`realtime.messages`)는 보안 규칙이 켜져 있고 정책이 0개라 지금은 아무도 채널에 들어올 수 없음(새 정책 필요). 연습용 마을은 운영 빌드에서 닫혀 있어 측정용으로 여는 환경 변수가 필요
  - **알려진 한계 (계획 단계)**: 캐릭터끼리는 부딪히지 않고 겹쳐 설 수 있음 / 꾸미기 값이 아직 3D에 반영되지 않아 모두 같은 모습(Task 014 뒤 반영 가능) / 목표만 주고받으므로 걷는 타이밍이 화면마다 조금 다를 수 있음(도착 자리는 같음)
  - ⚠️ **사용자가 직접 해야 하는 일**: Supabase 요금제 확인, 대시보드 Realtime → Settings의 "Allow public access" 끄기, 성능 시험 때 실제 휴대폰으로 확인, 켤 때 Vercel 환경 변수 `LIVE_WALK=1` 추가
  - 시간: Phase 4는 이미 추정 합계(약 36h)가 남은 시간(약 30h)을 넘으므로, 이 작업은 "12.25 전 필수" 작업(Task 015·020·021·022)보다 뒤 순서

## 로드맵 작성 시 확인한 PRD와의 차이·주의점

- **시작일 차이**: PRD 일정은 11.23 시작 기준(약 14h)인데, 오늘(11.25)까지 코드가 없어 실제 남은 시간은 약 11h입니다. LINE·카카오 등록을 11.23~24에 신청했는지도 확인이 필요합니다 (Task 001).
- **라우팅 순서 (11.25 사용자 결정)**: 화면 주소를 먼저 만들지 않고 **UI/UX를 먼저 만든 뒤** 라우팅을 진행합니다. 주소는 화면을 만들 때 함께 생기고(Task 004·005), 자동 이동 규칙은 로그인과 함께 만듭니다(Task 007). 그래서 Task 002는 1h → 0.5h, Task 007은 1.5h → 2h로 옮겼고 합계 시간은 같습니다. 초대 링크 주소 모양(`/invite/코드`)은 지인에게 링크를 보내기 시작하는 12.3 전에 확정해야 합니다(보낸 뒤 바꾸면 예전 링크가 안 열림).
- **작업 순서 차이**: 12.3 전/후 범위는 PRD 표와 같지만, 순서는 구조 우선 원칙에 따라 "화면(더미) → 데이터 연결"로 바꿨습니다. PRD 표는 데이터·로그인을 먼저 두었습니다.
- **PRD 일정표에 없는 일**: 12.27 새해 테마 전환 작업이 PRD 일정표에 없어 Task 024로 추가했습니다 (내용 미정). 12.27 이후에도 편지를 읽을 수 있는지도 PRD에 적혀 있지 않습니다.
- **PRD 안의 작은 불일치**: 일정 위험 2는 12.3 이후로 미룬 것을 "낮/밤·편지 읽기"로 적었고, 가정 21은 여기에 "인증샷·알림"을 더 적었습니다. 이 로드맵은 PRD 일정표(넓은 쪽)를 따랐습니다.
- **Phase 4 시간 초과**: 12.3 이후 기능 추정 합계(약 36h)가 가능 시간(약 30h)보다 많아서, 진행률 게이지·커플 마을·인증샷은 [여유 있으면]으로 표시했습니다. 이 기능들이 모두 "확정 기능"이라는 점은 그대로이며, 우선순위는 회의에서 정해야 합니다.
